# 端末貸出管理システム システム調査および改善提案レポート

本レポートは、1台のChromebook（Linux Mint OS）上のローカル環境で動作する「端末貸出管理システム」について、ソースコードの精査および一時的なモック環境を用いた実動作確認に基づき、システムの問題点・構造的課題・改善提案を網羅的に取りまとめたものです。

---

## 1. 総評

本システムは、「ローカルSQLiteを正データとし、ネットワーク断や外部連携不調時も12扉の貸出・返却・施錠を止めない」というフェイルセーフ設計が極めて堅牢に実装されています。単一Chromebookによるキオスク端末運用という大前提に即したセキュアなローカルバインド（`127.0.0.1`限定待ち受け）、CSRF防御（`Sec-Fetch-Site`検証）、認証トークン管理、バックアップ保護など、全体的に高い完成度を有しています。

一方で、直近行われた変更（返却チェックリストの改善）において、**画面表記とプログラムロジックが真逆に解釈される深刻なロジック不整合（バグ）**が混入していることが判明しました。また、1ファイルに数千行が集中する単一肥大化構造、GAS（Google Apps Script）との全体スナップショット同期による将来的な通信負荷、運用者（専門知識を持たない教職員）が異常発生時に自力復旧しにくい点などが課題として挙げられます。

### 最も深刻な問題トップ5
1. **返却チェックリスト「破損なし/あり」の判定ロジック反転バグ**（`index.html:637` / `js/app.js:2206`）
   画面には「破損はありませんか？」と表示されているのに対し、コード上はチェックボックスがオン（`true`）の時に「破損あり」と判定されるため、生徒が「破損なし」のつもりでチェックを入れると破損報告画面が開いてしまう。
2. **ローカル返却時の破損報告に対する管理者即時通知の漏れ**（`local-db/lending.js:929` / `gas/Code.gs:3158`）
   ローカルDBで返却・破損処理を行った際、故障テーブルへの記録は行われるが、GAS側の即時通知メール送信関数が呼び出されず、メール通知を有効にしていても管理者に通知が届かない。
3. **ウェルカムダイアログ非表示化に伴うデッドコードおよび不要CSSの残留**（`js/app.js:2842` / `css/pages.css:4443`）
   ダイアログの表示呼び出しは削除されたものの、関数の定義（56行）やCSSアニメーション定義（120行以上）がそのまま残存している。
4. **延滞発生時の即時アラート送信トリガーの欠落**（`local-db/lending.js:920`）
   返却時に延滞が発生した場合、ローカルDBの延滞回数は加算されるが、即時通知メールがキューイングされず、GAS側の定期タイマー実行（15分間隔）に依存している。
5. **扉9〜12（MCP23017 0x24側）のセンサービット割り当ての未検証**（`arduino_sketch/arduino_sketch.ino:42`）
   スケッチ内のコメントにある通り、扉9〜12のセンサー配線ビット割り当てが暫定値のままであり、実機設置時に `r` コマンドによる実測確認が行われないと誤検知の原因となる。

### 現システムの最大の課題トップ3
1. **モノリシックな巨大ファイル構造**（`server.js` 約3650行、`js/app.js` 約2900行）
   機能追加やバグ修正時に副作用が発生しやすく、保守性・テスト容易性を低下させている。
2. **全体スナップショット送信方式による同期オーバーヘッド**
   履歴件数が増加するにつれてGASへのPOSTボディが肥大化し、タイムアウトや帯域圧迫のリスクが高まる。
3. **非専門家（教職員）向けの障害自己診断・ガイドUIの不足**
   ネットワーク断・USB切断・停電復旧時に、管理画面を見ても具体的な復旧手順が指示されず、手動操作のハードルが高い。

### 最も効果の高い改善提案トップ3
1. **【クイックウィン】返却チェックリストの選択UIおよび判定ロジックの修正**
   直近のバグを即座に修正し、「破損なし」「破損あり」を明示的な2択ラジオボタンに刷新する。
2. **【クイックウィン】ローカルイベント発生時のGAS通知メール連携の補完**
   ローカルDBでの故障登録・延滞判定時に、メールキュー経由でGAS通知をトリガーする仕組みを追加する。
3. **【中期改善】サーバー側・フロント側の機能別モジュール分割（リファクタリング）**
   ルーティング・ビジネスロジック・シリアル通信・同期処理を責務ごとに分離し、保守性を劇的に向上させる。

### 「直近で行われた変更」の3点の検証結果

1. **起動時の「端末貸出管理システムへようこそ」ダイアログを、表示しないように変更した。**
   - **検証結果**: **問題あり（コード残骸あり）**
   - **詳細**: 初回起動、再読み込み、タイムアウト後のリセット、Arduino再接続後などのすべての経路においてダイアログが表示されないことを確認しました。しかし、`js/app.js` (2842〜2898行) に `showTutorialIfFirstTime` や `showTutorial` などの関数定義（56行）が残っており、`css/pages.css` (4443〜4560行) にも120行以上のチュートリアル用CSSスタイルが残存しています。また `js/ui.js` (114行) に不要な要素削除コードが残っています。

2. **返却チェックリストの「端末に破損はありませんか」の項目が、初期状態でチェック済みになっていたのを、未選択に変更した。**
   - **検証結果**: **問題あり（重大なロジック反転バグ）**
   - **詳細**: 初期状態で未選択（`_chkState[3] = false`）になるように変更されていますが、`index.html` (637行) のタイトルが「端末に破損はありませんか？（破損がある場合はチェックを外してください）」となっているのに対し、`js/app.js` (2206行) の判定コードは `const hasDamage = _chkState[3];` となっており、**「チェックが入っている＝破損あり」** と扱われます。このため、生徒が「破損なし」を意図してチェックを入れると破損報告アラートが表示され、逆にチェックを入れない（未選択の）まま他の2項目をチェックすると「破損なし」として返却できてしまいます。

3. **破損がある場合は、ログアウト画面の確認などの他のチェックを省略して、返却できるようにした。**
   - **検証結果**: **問題なし（一部通知漏れあり）**
   - **詳細**: 破損を選択して返却を進める場合、ログアウトチェック（項目1）およびシャットダウンチェック（項目2）が正しく省略され、即座に扉解錠・返却フローへ進めることを確認しました。また、以下の仕様維持を確認しました。
     - **履歴・ログ・スプレッドシート**: 破損の事実（`isDamaged: true`）がローカルDBに記録され、`failures` テーブルへ「故障中」として自動登録されます。
     - **次回の貸出対象からの除外**: 故障中として登録された端末は `getAvailableDevice` / `_pickBestDevice` の候補から正しく除外されます。
     - **返却の物理確認**: センサーによる返却確認および手動完了時の「棚に戻したことの確認」ステップは省略されずに維持されます。
     - **訂正可能性**: 管理者は「故障端末」タブから「修理完了」を押すことで貸出可能状態に戻せます。また「貸出・履歴」タブから履歴の編集が可能です。
     - **注意点**: 前述の通り、ローカル返却時に管理者へ即時通知メールが送信されない不具合があります。

## 4. 問題点の詳細

### No.1: 返却チェックリストの判定ロジック反転バグ
- **該当箇所**: `index.html` 637-638行目、`js/app.js` 2206-2207行目
  ```html
  <!-- index.html -->
  <div class="chk-title">端末に破損はありませんか？</div>
  <div class="chk-desc">破損がある場合はチェックを外して、先生への報告手順に進んでください</div>
  ```
  ```javascript
  // js/app.js
  const hasDamage = _chkState[3];
  const noDamageAllOk = !_chkState[3] && _chkState[1] && _chkState[2];
  ```
- **何が問題か**: UIのテキストは「破損はありませんか？（破損がある場合はチェックを外す）」となっているため、**チェックを入れる＝破損なし** という意味になります。しかしJavaScriptのコードでは `_chkState[3]`（チェックが入っている状態＝`true`）を `hasDamage = true`（破損あり）として判定しています。
- **発生条件と影響**: 返却操作を行うすべての生徒に影響します。生徒が「破損はありません」と確認してチェックを入れると、画面に「端末の損傷を報告してください」という赤い警告バナーが表示されます。逆にチェックを入れずに放置すると「破損なし」として返却できてしまいます。
- **再現手順**:
  1. トップ画面から「返却」をタップし、返却対象を選択する。
  2. 返却チェックリスト画面で「端末に破損はありませんか？」のチェックボックスをタップしてチェックを入れる。
  3. 「端末の損傷を報告してください」というアラートが表示される。
- **推奨する修正方法**: UIを明確な2択（「破損なし」「破損あり」のボタン選択）に変更するか、またはコード側の論理を一致させます。
  ```javascript
  // js/app.js 修正案（破損なし＝true の場合）
  const noDamageChecked = _chkState[3];
  const hasDamage = !_chkState[3]; // 未チェックを破損ありとして扱う場合
  ```
- **修正の優先度と工数の目安**: **優先度: 致命的 / 工数: 小（1〜2時間）**

---

### No.2: ローカル返却時の破損報告に対する管理者即時通知の漏れ
- **該当箇所**: `local-db/lending.js` 929-932行目、`gas/Code.gs` 3158-3175行目
  ```javascript
  // local-db/lending.js
  if (params.isDamaged === true || params.isDamaged === 'true') {
    try { reportFailure({ deviceId: result.deviceId, name: result.name, email: result.email, loanId }); }
    catch (e) { console.error('[returnComplete] reportFailure エラー: ' + e.message); }
  }
  ```
- **何が問題か**: ローカル処理で `returnComplete` が実行された際、`reportFailure` が呼ばれてローカルの `failures` テーブルにデータが保存されます。その後 `scheduleSync()` によってGASへスナップショットが送られますが、GAS側の `syncFromLocal` はスプレッドシートの行を置換するのみで、即時通知メール送信 (`_sendFailureReportedEmail`) を実行しません。
- **発生条件と影響**: 生徒が破損ありで返却し、運用設定で `notifyEmailEnabled: true` かつ `notifyOnFailure: true` に設定されている場合に発生します。管理者に破損通知メールが即座に届かず、管理者がスプレッドシートや管理画面を直接開くまで破損に気づけません。
- **再現手順**:
  1. 運用設定でメール通知を有効にする。

## 5. システム全体の課題（現状分析）

### 1. 運用面の課題
- **専門知識を持たない教職員の負担**: 端末の追加・廃棄、卒業生の削除、年度替わりの一括処理を行う際、管理画面の操作が分散しており間違いやすい。
- **障害発生時の復旧の難しさ**: Arduino切断やNTP時刻未同期などの警告バナーが表示されても、具体的な復旧手順（USBケーブルの挿し直しや `dialout` 権限のコマンド等）が画面上に表示されず、教職員が自力で解決できない。
- **停電・再起動時のデータ保全**: 6時間おきの自動バックアップとWALモードによりデータ消失リスクは低いが、復元操作には「貸出中データがないこと」などの条件があり、手順の理解が必要。

### 2. データ管理・プライバシーの課題
- **個人情報の保持とログ**: 生徒の氏名・メールアドレス・生年月日がローカルSQLite、ログファイル（`server.jsonl` / `audit.jsonl`）、および録画メタデータに保存されている。
- **スプレッドシートへの同期範囲**: 閲覧用ミラーとして氏名・メールアドレスが全件送信されている。運用上問題ないが、個人情報保護の観点から閲覧権限の管理が必須である。

### 3. 信頼性・耐障害性の課題
- **単一障害点 (SPOF)**: Chromebook本体、USBケーブル、Arduino基板、電源が単一障害点となる。ただし、ネットワーク断やGAS障害時にはローカル完結で貸出・返却を継続できる優れた耐障害性を備えている。
- **物理故障への対応**: 電磁ロックの不具合や扉の引っ掛かりに対し、管理画面からの強制解錠機能および手動記録機能が用意されている。

### 4. 設計・保守性の課題
- **ファイル肥大化**: `server.js`（3650行以上）、`js/app.js`（2900行以上）にルーティング、データ操作、画面制御、カメラ処理、タイマー管理が混在している。
- **テストの網羅性**: 正常系の単体テストは存在するが、競合状態（同時貸出・同時返却）、シリアル通信切断時の復旧、破損返却フローの結合テストが不足している。

### 5. 拡張性の課題
- **設定・ハードコードの分散**: 端末ID一覧（`CB-01`〜`CB-12`）が `js/config.js`、`Code.gs`、`arduino_sketch.ino` の3箇所に個別にハードコードされており、扉数変更時の修正漏れリスクが高い。

### 6. 利用者体験 (UX) の課題
- **生徒向けUX**: 返却チェックリストの破損項目におけるロジック反転バグにより、正しく操作した生徒が困惑する。
- **管理者向けUX**: システム全体の健康状態が一目でわかるダッシュボード（Arduino接続、カメラ状態、同期状態、空き容量の統合表示）の視認性向上の余地がある。

## 7. UI/UXの評価と改善提案

### 指示された8つのUI/UX問題点の詳細と改善対応結果

#### キオスク画面（`index.html`）

1. **① 生年月日の入力例が分かりにくい**
   - **現状の問題**: プレースホルダーが `placeholder="YYYY MM DD"` とスペース区切りで表示されていたが、オンスクリーンキーパッドでの実際の入力はハイフンやスペースなしの8桁連続数値（例: `20130509`）。入力例のテキストと実際の入力形式が矛盾し、生徒が迷う原因となっていた。
   - **改善対応**: プレースホルダーを `placeholder="例: 20130509"` に変更し、8桁連続入力であることが一目でわかるように直感的な表現へ統一。

2. **② 返却画面で名前一覧が空のときのフォールバック表示**
   - **現状の問題**: 貸出中の端末が0件の際、`#return-loan-list` コンテナが空のままとなり、画面上に明確なメッセージが表示されなかった。
   - **改善対応**: HTMLの初期構造および `renderReturnList()` のフォールバック描画に、アイコン付きの空状態メッセージ「現在貸出中の端末はありません（端末を借りていない場合、返却の必要はありません）」および「トップに戻る」アクションボタンを配置。

3. **③ 貸出完了画面の「手動で貸出を完了する」ボタンの唐突さ**
   - **現状の問題**: 扉センサーの応答がない場合に、手動完了ボタンが何の説明もなく最上部に突如出現するため、ユーザーが何をすべきか判断しにくかった。
   - **改善対応**: ボタンの直前に視覚的に目立つ警告カード（`manual-notice-card`：黄色の警告アイコン＋「扉の状態を確認できません。端末を取り出し/戻し、扉を閉めたことを確認の上、手動で完了してください」の説明文）を明確に配置し、説明を読んでからボタンを押す自然な導線へ改善。

4. **④ 返却チェックリストでチェック項目1だけ挙動が異なる不統一感**
   - **現状の問題**: 項目2・3は直接タップでチェックを入れる形式だが、項目1だけはボタンを押してカメラ自動確認（または手動確認）画面へ遷移する方式となっており、操作モデルが不統一で戸惑いやすかった。
   - **改善対応**: 項目1の説明文に「カメラ確認ボタンから進むか手動確認を行ってください」という導線案内を明記し、確認完了後は他項目と同様に緑色のチェックバッジが付く視覚的フィードバックを統一。

5. **⑤ 「扉を閉める」ヒント文言の重複・冗長感**
   - **現状の問題**: 貸出完了・返却完了の両方のステップ3カードに「扉の上の方を押すと閉まりやすいです。ゆっくり押し込んでください。」という長文が全く同じ文言で重複して出ていた。
   - **改善対応**: ステップ3の文言を「カチッと音がするまでゆっくり押し込んでください。」へ整理・集約し、シンプルで強調されたClosing案内に改善。

#### 管理者画面（`admin.html`）

6. **⑥ サイドバーの「バックアップ」アイコンの視覚的不一致**
   - **現状の問題**: ナビゲーションの「バックアップ」タブのアイコンがデータベース（円柱）アイコンであり、保存・バックアップダウンロードの文脈と視覚的に合致していなかった。
   - **改善対応**: アイコンを専用の「保存・アーカイブ（トレイ＆ダウンロード矢印）」SVGアイコンへ変更し、バックアップとデータ保存の機能であることが直感的に伝わるデザインに刷新。

7. **⑦ ダークモード/ライトモード切替の全体テーマ一貫性**
   - **現状の問題**: ダーク/ライトテーマの切替ボタンが `admin.html` にしか存在せず、キオスク画面（`index.html`）に保存テーマが反映されていなかった。
   - **改善対応**: `js/ui.js` の初期化時に `localStorage.getItem('admin-theme')` を読み込み、`document.documentElement.setAttribute('data-theme', saved)` を自動適用する仕組みを追加。キオスク画面と管理画面で統一されたテーマ表示を実現。

8. **⑧ Topbar 接続ステータスバッジのクリッカブル表示**
   - **現状の問題**: `topbar-conn-status` に `role="button"` やクリックイベントが設定されているものの、見た目が単なるテキストバッジであり、クリックして詳細ヘルスチェックが開けることが視覚的に判別できなかった。
   - **改善対応**: `css/admin-base.css` の `.topbar-status` にボタン風のボーダー、`cursor: pointer`、ホバー時の背景色変化（`--surface-hover`）、クリック時の押し込みアニメーション (`transform: scale(0.97)`)、フォーカスリングを付与し、明確にボタンとして認識できるスタイルへ改善。
